# AGENTS.md: how to set up and run RE-PEAT

For anyone (person or coding agent) picking up this repository. Last updated 2026-11-12. Read this, then the document it points
you to; `docs/README.md` has the full map.

## What this repo is

The hub of the RE-PEAT peatland rewetting toolkit. It holds little analysis code: that is in six module repositories
(`repeat-common`, `repeat-dem`, `repeat-delineation`, `repeat-neraca`, `repeat-prioritisation`, `repeat-pump`, all under
github.com/Re-Peat-Project). The hub ties them together:

- `tools/khg_pipeline.py`: the runner of the full chain per KHG (DEM preparation, sub-KHG delineation, water balance,
  prioritisation, canal-block plan), once per DEM. Its steps are in `tools/pipeline/steps.py`.
- `pipeline.yaml` and `sites/<folder>/`: the settings (national template, per-KHG facts and overrides) for all 865 KHG.
- `docker/`: the image of the whole chain, the compose setup for running it, the batch settings for a server.
- `env/`: the exact package versions of the four Python environments and the commit of each module repository.
- `docs/`: background, methods, data, and the guides below.

## Run it (preferred): Docker

Nothing to install but Docker. The image is published at `ghcr.io/re-peat-project/repeat-chain` (public), built by
`.github/workflows/repeat-chain-image.yml` on every change to the chain's code, settings or locks.

1. Follow [docs/22-running-on-your-machine.md](docs/22-running-on-your-machine.md): `docker/compose.yaml` and
   `docker/peer.example.env` (one folder `REPEAT_DIR`, your own Earth Engine project), `ee-auth` once, `ee-check`, then
   `docker compose run --rm chain run --khg <code>`.
2. Data: the national core files (1.92 GB) and SiTMAT come as a data pack on the team's shared drive
   (`tools/peer_data_pack.py` makes it). LiDAR is restricted and not shared; bring your own in `data/lidar_own/`. DeltaDTM and
   ICESat-2 are downloaded by the chain. DEMNAS is optional (your own Tanahair link in `TANAHAIR_LINK`).
3. Settings: [docs/23-configuring-a-run.md](docs/23-configuring-a-run.md). Every option, with complete examples:
   [docs/21-configuration.md](docs/21-configuration.md) and [docs/config/](docs/config/).
4. Many KHG at once (a server): `tools/national_run.py` with `docker/batch.example.toml`; see [docker/README.md](docker/README.md).

## Develop: a workstation

For changing the modules or running without Docker.

1. Clone this repository and the six modules side by side in one folder (the workspace);
   `python tools/khg_pipeline.py setup --clone` clones the missing ones at the locked commits.
2. Build the four environments from `env/*.lock.txt` (`main` in `<workspace>/.venv`; `dem`, `delineation`, `pump` in their
   repositories' `.venv`): README section "Set up a workstation", and [docs/19-running-the-pipeline.md](docs/19-running-the-pipeline.md).
3. `python tools/khg_pipeline.py setup` must say `ready` (repositories at the locked commits, interpreters, package locks).
4. Point `REPEAT_DATA` at the data folder and `REPEAT_KHG` at the work folders, or set `data` / `khg_root` in an untracked
   `pipeline.local.yaml` (with your interpreters and `EE_PROJECT`).
5. Then `status`, `plan`, `run` as in the README, section "Run the chain".

## Commands to know

    python tools/khg_pipeline.py status | plan | run --khg <code> [--dem ...] [--from <step>]
    python tools/khg_pipeline.py config validate [--khg ...]   # check settings and files before a run
    python tools/khg_pipeline.py config show --khg <code>      # every setting a KHG's steps read, and where it comes from
    python tools/khg_pipeline.py config catalogue              # regenerate docs/21 and docs/config/ after a schema or pipeline.yaml change
python tools/khg_pipeline.py setup [--clone] [--lock]      # check the setup; --lock rewrites env/*.lock.txt after module commits are pushed
    python tools/khg_availability.py [--workers 4]             # the per-KHG data table (docs/20); khg_availability_ee.py adds the Earth Engine columns

In Docker, the same commands follow `docker compose run --rm chain` (for example `... chain config validate --khg <code>`).

## When you change something

- **A module:** commit and push it, then `setup --lock` here and commit `env/`, so the image and other machines get the same
  commit. The workflow rebuilds the image; check that its run passes before telling anyone to pull.
- **A setting the chain reads:** add it to `tools/pipeline/schema.py` (English title, Indonesian label, unit, allowed values),
  then `config catalogue`. `config validate` must pass for all KHG before a batch run.
- **Per-KHG settings:** never edit `sites/<folder>/khg.yaml` (generated by `init`); exceptions go in `overrides.yaml` next to it,
  each with a reason and a date.
- **Docker image:** `docker/Dockerfile`; packages left out of the image in `docker/exclude.txt`. Test with
  `docker compose run --rm chain setup`.

## Rules of the project

- Every number in a document or report comes from a file or a fetched source; say which.
- Everything must be reproducible from config, for any KHG. No hand-made outputs.
- Never downscale or coarsen data to make a run fit; use tiled or windowed processing.
- Ask before deleting, overwriting or sending anything out (data, results, messages).
- Data rights: KLHK LiDAR, SiTMAT and other government or licensed data stay inside the team; they never go into a repository,
  the image or a public output without clearance from KLH and the World Bank. `_data` is not tracked.
- Commit only when asked, under the person's own name; no AI attribution in commits or files.
- Writing: plain prose. Dashboards: visual first, light and dark themes, English and Bahasa Indonesia labels.
- A laptop with 16 GB runs out of memory above about 4 parallel raster workers.
